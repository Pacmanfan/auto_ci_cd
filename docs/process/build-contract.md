## Build

The build is configured in `devsys.json` `build` and run through the adapters
of `scripts/devsys_build.py` (REQ-DEVOPS-049, ADR-000199):

```bash
python3 scripts/devsys.py build check      # the adapter's tools are present
python3 scripts/devsys.py build build      # configures a tree that is not configured, then builds
python3 scripts/devsys.py build rebuild    # clean + build; `fresh` deletes the tree first
python3 scripts/run_tests.py --build ...   # build, then test
```

| `build.system` | configure | build | clean |
|---|---|---|---|
| `none` | — | NOT CONFIGURED (exit 10), never success | — |
| `make` | — | `make -C <build_dir if it has a Makefile, else source_dir> -j<jobs>` | `make ... clean` |
| `cmake` | `cmake -S <source_dir> -B <build_dir>` | `cmake --build <build_dir> -j <jobs>` | `--target clean` |
| `qmake` | `qmake6|qmake <source_dir>/<tests.root_project>` in `<build_dir>` | `make -C <build_dir>` | `make clean` |
| `custom` | `build.configure` | `build.build` (required) | `build.clean` |

Any adapter's commands can be replaced with argv lists in `build.configure`,
`build.build`, `build.clean` (`{build_dir}`, `{source_dir}`, `{jobs}` are
substituted); `build.timeout_seconds` bounds each step. Every action writes
`<build_dir>/build-results/<id>.json`, `latest.json` and the log, with the
failure class below.

Variants:

- `build/debug` — canonical for tests (debug configuration, with symbols for crash dumps).
- other shadow trees (e.g. `build/release`) — only when a task explicitly requires that variant.

Outputs (PROJECT-SPECIFIC):

- `build/debug/<APP_BINARY>` (main executable, unstripped debug recommended for forensics)
- `build/debug/<TEST_BINARY>` (one line per registered test binary)

## Tests

Tests run through the tiered orchestrator (REQ-DEVOPS-046, ADR-000186):

```bash
python3 scripts/run_tests.py --tier t2 --request requests/processing/<request>.md   # the work-item gate
python3 scripts/run_tests.py --plan --tier t2 --request <file>                      # what would run, and why
python3 scripts/run_tests.py --tier t3 --build-dir build/release                    # full regression, Release tree
```

| Tier / lane | Runs | Budget (`scripts/test_manifest.json`) |
|---|---|---|
| t0 | devsys structure, drift / doc-integrity / invariant audits — always | 60 s |
| t1 | t0 + unit groups of the affected suites (the project's unit suites, the process-script tests, the audit tests) | 240 s |
| t2 | t1 + integration / GUI groups of the affected suites | 900 s |
| t3 | every suite and group, affected or not | nightly / pre-release |
| perf, stress, soak, live, package | benchmarks and throughput assertions, stress groups, long soak runs, live `verify_*.py` scripts (`live_scripts` in the registry), the project's package validation + smoke test | explicit only, one at a time |

The suites, their groups, tiers, shards, inputs and requirements are
registered in `scripts/test_manifest.json` (`--list`). Affected suites are
derived from the qmake project graph (`scripts/test_selection.py`) when
`tests.selection` is `qmake` (or `auto` with a root `.pro`), otherwise from
each suite's `sources` / `inputs` globs; a changed path nothing claims
selects everything. Results are read from the exit code, PASS / FAIL lines,
JSON lines (`$PROJECT_TEST_RESULTS`), JUnit XML (`"results": "junit"`,
written to `$PROJECT_TEST_JUNIT`) or TAP (`"results": "tap"`); a failed case
fails its group even when the process exits 0. A run in which nothing
executed is **EMPTY** (exit 4) and a run stopped by a signal
**INTERRUPTED** (exit 130) — neither is ever PASS or satisfies the gate
(REQ-DEVOPS-050). The log of every job that did not pass is kept beside the
run record (`<build>/test-results/runs/<run id>/`). A group whose binary (GNU build id)
and inputs are unchanged since it last passed is CACHED. A crash or hang is
attributed to the case it happened in (CRASH / TIMEOUT) and the rest of that
shard still runs; cases that need real hardware run in the live lane only
(`PROJECT_LIVE_HW_ARGS`). Every run writes
`<build>/test-results/runs/<run id>.json`; link it from the work record
(`**Test-Run:**`), which `scripts/completion_gate.py` checks, and copy it to
`evidence/VER-NNNNNN/run-<run id>.json` (build trees are local; the gate reads
either). `python3 scripts/evidence.py create --work W --test-run <run id> ...`
does both.

Runners (direct use, PROJECT-SPECIFIC): selection flags accumulate
(`<runner> --unit --integration` runs both), `--filter` repeats, per-case
watchdogs, and the environment contract `PROJECT_TEST_SHARD`,
`PROJECT_TEST_CASES`, `PROJECT_TEST_LIST`, `PROJECT_TEST_RESULTS`, implemented
by the project's test framework (`<PROJECT_TEST_FRAMEWORK_HEADER>`).

## CI entry point

```bash
python3 scripts/devsys.py ci --tier t2 [--base origin/main] [--audit standard] [--verify-commits A..B]
python3 scripts/devsys.py verify-commit HEAD        # the commit carries the code its gate verified
```

`ci` runs, in order:

1. configuration and structure;
2. the build adapter;
3. the test tier;
4. drift / doc integrity / invariants;
5. the architecture audit (`--fail-on fail`);
6. `verify-commit` over the range.

Each step is PASS / FAIL / SKIPPED / UNKNOWN. The record is written to
`<build_dir>/ci-results/<id>.json` and `latest.json`. Exit codes: 0 PASS,
1 FAIL, 3 UNKNOWN. `ci` claims, moves and commits nothing. A CI job runs it
on a clean checkout of the commit, and publishes the record and the run
record as its artifacts (REQ-DEVOPS-051).

## Distinguish Failures

Autonomous loop must classify:

- `SOURCE ERROR` — compilation error (syntax/type).
- `TEST FAILURE` — assertion failed.
- `LINK FAILURE` — undefined reference, missing lib.
- `DEPENDENCY FAILURE` — missing library / framework (PROJECT-SPECIFIC list).
- `ENVIRONMENT FAILURE` — display, hardware, live data rate.
- `TOOL FAILURE` — qmake/make not found.
- `TIMEOUT` / `RESOURCE FAILURE` / `UNKNOWN`.

`scripts/devsys_build.py` assigns these classes (SOURCE, LINK, DEPENDENCY, TOOL, ENVIRONMENT, TIMEOUT, RESOURCE, UNKNOWN) from the build output; the log in `<build_dir>/build-results/` is the evidence.

## Targeted vs Broad Validation

Selection is computed, not chosen: `scripts/run_tests.py --request <file>`
selects the suites whose projects or inputs the request's registered paths
affect (`--plan` shows why each runs). While iterating, narrow further with
`--suite ID` or a runner's `--filter`; before completing a work item run t2;
changes to global build files, protos or unmapped paths select everything by
themselves. t3 (every suite, Debug and Release trees) is the pre-release run.

## Structured Build/Test Evidence

Every build/test run invoked by the autonomous loop must produce evidence sufficient for another agent to continue:

- command, configuration (build dir, toolchain version), result, timestamp, relevant output/log path, artifact if applicable.
- For application changes, record actual counts and classification (`PASS`, `EXPECTED / PRE-EXISTING`, `REGRESSION`, `BLOCKED / ENVIRONMENTAL`) per `docs/requirements/development_operations.md` REQ-DEVOPS-009/010, and the `scripts/run_tests.py` run id (`**Test-Run:**`); its statuses map as PASS / CACHED → PASS, EXPECTED → EXPECTED / PRE-EXISTING, STALE / MISSING / BLOCKED / ENVIRONMENTAL → BLOCKED / ENVIRONMENTAL, FAIL / TIMEOUT / CRASH → a failure to classify (REGRESSION or pre-existing), FLAKY → passed alone, investigate.

Evidence location: `evidence/VER-NNNNNN-*.md` with manifest entry in `evidence/evidence.txt`.

## Hard Invariant

> NEVER CLAIM A TEST PASSED UNLESS IT RAN.

Valid verification states: `NOT_RUN`, `RUNNING`, `PASSED`, `FAILED`, `BLOCKED`, `NOT_APPLICABLE` (maps to `pending|pass|fail|blocked` in `docs/process/state-model.md`). A run that could not execute is `BLOCKED`, not `pass`.

Record: command, configuration, result, relevant output/log, timestamp, artifact.

## Health

`scripts/build_health.py` (or `scripts/health_check.py`) answers "Can the autonomous system currently build and verify?" — checks missing dependencies, failed tests, stale generated files, broken automation, environment.

`scripts/worktree_check.py` (safe clean worktree check) answers "Is the worktree safe to mutate?" — inspects `git status --porcelain`, unrelated changes, generated files, build artifacts; never overwrites unrelated human work.

## Relation to Lifecycle

`BUILD → TEST → VERIFICATION` is the `IMPLEMENT → TEST → VERIFY` slice of the canonical `Request → Requirement → Work → Implementation → Test → Verification → Documentation → Complete` lifecycle. It is always reached via `work/active/WORK-NNNNNN.md` and leaves evidence `VER-NNNNNN`.

See also: `docs/process/autonomous-operating-model.md`, `docs/process/recovery.md`.
